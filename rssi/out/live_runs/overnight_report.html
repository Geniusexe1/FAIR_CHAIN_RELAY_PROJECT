FAIR Chain–Relay · overnight run log · 4–5 November 2026

Four NUCs, three relays: what the night showed

The big NUC now runs the simulation, map, chain robot and coordinator, and UNIST was fully mapped live at P0 −45 in about 97 minutes, with one manual coordinator restart. That run did not use all the relays. Your suspicion about the collision avoidance held up, and the night turned up two network problems that decide how the system can be laid out.

Your questions, answered

Did the 4-NUC layout work?
Not as you asked. With relay brains on NUC1, NUC2 and NUC3 the big NUC's radio link collapsed, so every recorded run has all three brains on the big NUC. NUC1–3 sat idle and the mesh carried no ROS traffic. The cause and what to try next are below.
Did the map get fully explored?
UNIST yes, hospital no. UNIST reached 100% of the reachable floor at P0 −45 with toned-down avoidance. It stuck at 84% until I restarted the coordinator by hand, which cleared its memory of rejected goals; after that it finished in about 13 minutes. Hospital reached 18.7% at P0 −50. A hospital run at P0 −45 with the reset fix is running now and is not in the table yet.
Is the toned-down avoidance better?
On this evidence, yes. At the same P0 it went further (67.8% against 58.9% and 56.1%) with no aborted plans, and the only full map came with it. The right-of-way logic I wrote never fired in either full run, and the abort guard fired 25 times in one of them, mostly stopping the client over and over beside relay2. These are few runs and each ended differently, so treat it as a strong hint.
Has RTF improved?
No. UNIST fell from a median of 0.31–0.35 to 0.27–0.28; hospital was 0.15, against 0.16–0.21 before. This is not like for like: there is one more relay and all three brains now share the machine with Gazebo. Other load on it may also hold RTF down, and I did not isolate that.
Which P0 uses all the relays?
UNIST −55 was the only value that used all three offline, though at most two at once, and it reached 84.4%. Hospital −50 used all three and reached 97.4%, with all three in one route for 2 moves. Live, no run routed through all three at once. The two P0 −50 and −55 runs that used relays most stalled at 56–68%; the full map came at −45, where only relay1 and relay2 carried traffic, one at a time, and relay3 stayed parked. So you do not yet have a value that both uses all relays and finishes. Going lower did not help offline: at −60 and −65 the plans fall apart.
Is the 1 m gap gone?
The gap in the code was 0.8 m and is now 0.5 m. I kept that much because bodies touch at about 0.35 m. The closest live approach was 0.35 m in a full run and 0.42 m in a toned-down run, and neither is a confirmed contact. I removed one impossible logger sample from the P0 −45 run, which showed a false 0.20 m. The logger samples poses only about every 14–25 s, so closer passes could have gone unseen.

Why the runs stopped short

  • Relays can't keep up with plans. Relays repeatedly miss waypoints and Nav2 logs "Failed to make progress". In one stretch relay3 covered about 5 m in 20 minutes. Once a plan fails, the planner often returns "no feasible plan" after 60–90 s of computing per goal, and nothing moves meanwhile.
  • The coordinator could trap itself. At 84% in the P0 −45 run it rejected the only goals left about 4,700 times: two had been blacklisted after transient failures and one sat beside the client. I added an automatic reset after 120 sim seconds without an accepted goal. It has not yet fired in a live run; the manual restart cleared the same memory. The −50 and −55 runs ended differently, with failed plans, but may also get further with it.
  • The offline simulator is optimistic. It reached 97–100% at values where live runs at −50 stalled at 19–65%, because its relays always arrive. Live, those moves are what fails.
  • Control rate suffers on the shared machine. Each relay logged 100+ "Control loop missed" warnings against its 20 Hz target in big_u_full2. I have not shown this causes the stalls.
  • Crashes cut two runs short. See below. The P0 −45 run lasted about 97 minutes without a crash, which supports the fixes without proving them.

What I'd do next

  1. Re-run P0 −50 and −55 with the reset fix, to look for a value that both uses all the relays and finishes. This is the open gap between your two goals.
  2. Keep the toned-down avoidance (--yield-r 0 --guard 0) as the default and remove the right-of-way code unless you want it kept. It is a settings change, so tell me which you prefer.
  3. Fix why relays miss waypoints, since that is what stops exploration. Start with one relay's Nav2 logs and a corridor drive test, then cut time wasted on repeated failed plans.
  4. Get the brains back onto their NUCs. First try: debug the composition segfault, or test CycloneDDS with a peer list. I have not tested Cyclone. Fewer processes across the radio is the goal.
  5. Give the hospital far more time. It runs at about half UNIST's RTF and has more to map.

What I changed on the machines

The system blocked my attempt to turn off the big NUC's screen lock, and I left that setting alone. The Gazebo videos come from capturing the window directly and were unaffected.
  • Big NUC: firewall rule dropping 224.0.0.7 on the mesh port (gone after a reboot); a virtual 2560×1440 display; xset s off -dpms for this login session; a new relays container from mesh_sim:humble, copied from NUC1.
  • Chain robot: no code or config files changed. Its container's .bashrc now sets IGN_IP, ROS_LOCALHOST_ONLY=1 and a higher file limit, added by the launcher. The Nav2 runtime parameters I told you about earlier are still applied at launch.
  • NUC1–3: containers restarted and test processes run during the debugging. A launch-file edit for the composition test was reverted.
  • Live intervention: at 08:22 I restarted the coordinator and explorer during big_u_nav2_P45, keeping the same map and robots. No robot was moved by hand tonight.
  • Code: pushed to main as commit cb82a2c; later fixes and the results are in a follow-up commit. RELAY_HOSTS=…/relay_hosts_bignuc.conf selects tonight's layout; without it, brains go to the NUCs.
